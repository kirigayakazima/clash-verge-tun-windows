# 2026-10-31 Windows TUN 断网复盘

## 环境与症状

- Windows，Clash Verge Rev 2.5.8，Mihomo 服务模式。
- 系统代理模式正常；切换 TUN 后，国内外网页均无法正常加载，浏览器出现 `ERR_CONNECTION_CLOSED`。切回系统代理立即恢复。
- 同时启用有线网卡、无线网卡以及名为 `vgate0` 的 Rust Wintun 虚拟网卡。O+ Connect 服务正在运行。
- TUN 原配置为 `auto-detect-interface: true`、`auto-route: true`、`stack: mixed`。物理出口网卡的 IPv4 `Forwarding` 为 `Enabled`。

## 排查与修复顺序

1. 确认系统代理的本地端口仍能连接，排除节点整体失效。
2. 查看 Windows 网卡：`vgate0` 为虚拟网卡，并报告很高的链路速率；物理出口是有线网卡，同时无线网卡也有默认路由。
3. 在 Clash Verge Rev 关闭“自动选择流量出口接口”；在当前订阅的“扩展覆写配置”加入 `interface-name: 以太网`。生成配置确认这两项已生效。
4. 确认有线网卡的 IPv4 转发仍为 `Enabled`，随后仅在 `ActiveStore` 暂时改为 `Disabled`。O+ Connect 服务保持运行。
5. 再次开启 TUN。Mihomo 虚拟网卡出现且为 `Up`；普通网站返回 HTTP 200，需要代理的网站可访问，外部检测显示所选代理的预期地区；有线网卡的转发保持 `Disabled`。
6. 重新登录 STOVE 后，首页及左侧游戏列表均显示《卡厄斯梦境》。此前在系统代理模式下该游戏页曾提示地区限制。

## 能得出的结论

这套组合在本机恢复了 TUN，重新登录后 STOVE 也显示了目标游戏。它与 [Clash Verge Rev 的 O+ Connect／IPv4 转发案例](https://github.com/clash-verge-rev/clash-verge-rev/issues/8117)和 [Mihomo 的虚拟出口误选案例](https://github.com/MetaCubeX/mihomo/issues/3122)高度一致。

**不能单独归因。** 本次同时固定了出口网卡和关闭了物理网卡的 IPv4 转发，没有做逐项反向复现；故障期间也没有保留下足够详细的核心日志。因此应称为“本机验证有效的修复组合”，而不是普适根因。

## 回退与长期注意事项

- 网络异常时，先在 Clash Verge Rev 关闭 TUN，恢复系统代理模式。
- `Set-Forwarding.ps1` 仅修改 Windows 的活动配置，并保存原值供恢复。运行前确认选中的是**真实物理出口**，不是 `Mihomo`、`vgate0` 等虚拟网卡。
- O+ Connect 可能重启后重新打开物理网卡转发。若故障复发，先读状态，不要直接卸载网卡或关闭安全软件。
- 本次已观察到 STOVE 的游戏展示恢复，但没有单独验证是 TUN 接管了哪个请求，也没有证明其他账号会得到相同结果。

# 2026-10-31 衍生故障：TUN 恢复后 Bilibili 桌面端与网页端视频黑屏无法播放

## 症状

- TUN 正常运行，海外与普通国内网站访问正常，STOVE 也能正常打开。
- 打开 Bilibili（桌面端应用及 Chrome 网页端）：
  - 首页推荐、UP 主信息、头像、视频标题、评论区、弹幕均能正常秒开显示；
  - 点进任意具体视频后，播放器窗口黑屏，中间显示 B 站内置的错误占位图（“你感兴趣的视频都在B站”），视频切片完全无法拉取加载。

## 根本原因

1. **B 站分流设计**：
   - 业务接口走 `*.bilibili.com`，被分流规则分给 `🌏 爱奇艺&哔哩哔哩` 策略组（该组默认处于 `DIRECT` 直连）。
   - 真实的音视频分片流走独立 CDN（如 `*.bilivideo.com`、`*.bilivideo.cn`）。分流规则将其归为 `🇨🇳 国内网站` 策略组。
2. **策略组状态异常**：
   - 本机在 Clash Verge Rev 中，`🇨🇳 国内网站` 策略组此前被误选为了 `🔰 选择节点`（即日本代理节点 `🇯🇵 日本A04 | IEPL`）。
   - 开启 TUN 后，整机视频流连接被无差别接管发往日本代理节点；而国内 CDN 节点对海外机房 IP 限制，或代理长连接握手挂起（实测 `curl` 10 秒超时）。
   - 播放器收不到切片数据触发异常，退化为 404 错误占位小电视。

## 排查与修复步骤

1. **定位策略组状态**：
   通过 Mihomo 内部控制接口查询发现：`🇨🇳 国内网站 -> now: 🔰 选择节点`。
2. **恢复直连**：
   - 将 `🇨🇳 国内网站` 策略组从代理节点切回 `DIRECT`。
   - 同步更新 Clash Verge 的 `profiles.yaml` 保存该状态。
3. **验证连通性**：
   - 修复前直接请求 `cn-sccd-ct-02-12.bilivideo.com` 视频切片：10 秒超时断开。
   - 修复后再次请求：0.1 秒内返回 HTTP 206 Partial Content，分片数据传输正常。
   - 浏览器刷新及桌面端重新进入视频，均恢复正常播放。

## 经验与防复发

- 国内流媒体“能开网页但看不了视频”是典型的“业务域名直连、CDN 域名走代理超时”症状。
- `Get-TunStatus.ps1` 脚本已增加对 `profiles.yaml` 中 `国内网站` 组的预警检测。
- `Test-Connectivity.ps1` 脚本已增加对 `bilivideo.com` CDN 直连握手的探测项。

# 2026-10-31 衍生故障：O+ Connect 静默重开转发致全节点 Timeout 与 gvisor 根治

## 症状

- 上午修复后正常运行数小时；中午切换到 TUN 模式时，突然全网断开或严重卡顿。
- Clash Verge Rev 节点测速中，**所有代理节点全部显示 Timeout（超时）**。
- 切回“系统代理模式”，节点延迟立刻恢复（50~80ms），国内外访问恢复。

## 根本原因

1. **ActiveStore 的易失性与 O+ Connect 的定时守护**：
   - 此前运行的 `Set-Forwarding.ps1 -Action Disable` 为了安全只修改了内存态 `ActiveStore`。
   - 后台常驻的 `O+Connect Service`（OPPO 跨屏互联服务）在执行设备重连、心跳检测或网络同步时，会以 SYSTEM 权限自动将物理网卡（以太网）的 IPv4 `Forwarding` 再次设置为 `Enabled`。
2. **`mixed` 堆栈发生握手回环死锁**：
   - 在 `stack: mixed` 下，Mihomo 尝试直接连接远端代理节点的底层 TCP 握手流量，被 Windows 启用了转发的网卡误导，重新卷入 TUN / `vgate0` 虚拟网卡中。
   - 内核触发回环阻断（`reject loopback connection`），导致内核无法与任何一台代理服务器建立握手，所有节点测速全线 Timeout。
   - 大量连接在 Windows 内部循环等待 5~10 秒超时，引发整机网络极端卡顿。
3. **系统代理模式不受影响的原因**：
   - 系统代理模式下完全卸载了 TUN 虚拟网卡及全局默认路由（`0.0.0.0/1`），Mihomo 通过标准 Socket 直连节点，不经过虚拟路由转发，因此秒级恢复。

## 排查与最终根治方案

1. **确认状态反弹**：
   运行 `.\scripts\Get-TunStatus.ps1`，发现 `以太网` 的 `Forwarding` 已反弹为 `Enabled`。
2. **临时止血**：
   以管理员身份运行 `.\scripts\Set-Forwarding.ps1 -Action Disable -InterfaceAlias "以太网"`，并退出 O+ Connect 客户端。
3. **架构根治（切至 `gvisor`）**：
   - 在 Clash Verge Rev 设置中将 TUN 的堆栈模式从 `mixed` 修改为 **`gvisor`**。
   - **原理与成效**：`gvisor` 是 Google 开发的用户态网络协议栈，在应用内存中自闭环组装数据包，不依赖 Windows 内核底层转发。切换后即便物理网卡转发开着，也不会再产生回环死锁，实现了对系统转发冲突的彻底免疫。

# 4. 2026-11-06 开机显示 Wi-Fi、TUN 开着直接修复无效与开机自愈任务

## 现象描述

1. **开机 Wi-Fi 回退**：
   - 电脑开机后，Clash Verge TUN 处于开启状态，但任务栏网络图标显示为 Wi-Fi，有线网卡显示无 Internet。
2. **TUN 开启时直接跑脚本无效**：
   - 如果不关闭 TUN，直接运行 `Set-NetIPInterface -Forwarding Disabled` 或修复脚本，有线网络依然无法恢复。
   - 必须先手动在 Clash Verge 界面关闭 TUN，执行修复脚本，然后再打开 TUN，有线网络才恢复正常。
3. **手动流程繁琐**：
   - 每次开机都需要反复手动关 TUN -> 开终端选菜单修复 -> 重新开 TUN。

## 根本原因深度分析

### 1. 为什么 TUN 开着直接改 Forwarding 无效？
- **TCP 连接与 Socket 生命周期**：Windows TCP/IP 协议栈对于正在运行的进程（特别是 Mihomo 核心绑定的底层 Socket 和 TUN 路由表项），只在 Socket 建立或网络接口状态突变时重新计算转发。
- **Mihomo TUN 缺少运行时热感知**：仅通过 PowerShell 修改物理网卡的属性，Mihomo 的 TUN 驱动（Wintun）并不会重新初始化；已经建立的系统路由和绑定仍然处于异常状态。
- **Windows NCSI 连通性探测滞后**：Windows 的网络状态指示器（NCSI，探测 `msftconnecttest.com`）在接口指标未发生重置时不会触发快速复测，依然维持“无 Internet”判断。
- **结论**：必须通过本地 Named Pipe（命名管道）给 Mihomo 发送配置变更信号，将 TUN 进行毫秒级的平滑“停用 -> 启用”热重启，使 Windows 路由表与 Socket 重新绑定。

### 2. 为什么开机优先显示 Wi-Fi？
- **服务启动竞争与 NCSI 多宿主回退（Multi-Homed Fallback）**：
  - 开机时，O+ Connect 等跨屏互联后台服务优先启动，将以太网的 IPv4 `Forwarding` 设为了 `Enabled`。
  - Clash Verge 开机自启动并加载 TUN。此时以太网由于转发冲突导致 NCSI 探测失败，Windows 将以太网标记为“无 Internet”。
  - Windows 网络管理器的多网卡回退机制触发，自动将默认流量退守到此时能够通过探测的次级网卡（Wi-Fi），因此托盘图标显示为 Wi-Fi。

## 根治方案设计

### 1. 零人工干预的全自动自愈 (`Invoke-AutoRepair.ps1` / `启动修复.cmd`)
1. **自动识别主物理出口**：按路由总度量值自动计算并锁定物理网卡（如“以太网”），无需人工手动选择。
2. **双库同步关闭 IPv4 转发**：同时写入 `ActiveStore`（内存态）与 `PersistentStore`（开机持久态），关闭数据转发。
3. **Mihomo Named Pipe 毫秒级热重载 TUN**：
   - 脚本通过 `\\.\pipe\verge-mihomo-production-*` 直接与 Mihomo 核心通信，发送 `{"tun":{"enable":false}}` 后延时 600ms 重新 `{"tun":{"enable":true}}`。
   - 用户**完全不需要手动关闭和重开 TUN**，脚本在后台秒级完成重载。
4. **国内策略组锁定 DIRECT**：自动核对并纠正 `🇨🇳 国内网站` 为 `DIRECT` 直连。
5. **刷新 DNS 与 NCSI 缓存**：执行 `ipconfig /flushdns` 促使 Windows 瞬间重新确认有线网络的 Internet 连通性。

### 2. Windows 计划任务实现开机“最优先”自愈 (`Install-StartupTask.ps1` / `安装开机自愈任务.cmd`)
要保证任务比用户软件更早生效，采用以下双触发器架构：
- **触发器 1：系统启动时 (`AtStartup`，最优先)**
  - 在 Windows NT 内核与 Task Scheduler 服务启动阶段立即运行，**早于任何用户登录，早于 Clash Verge GUI 与桌面软件**。
  - 以最高权限 `NT AUTHORITY\SYSTEM` 静默执行，无控制台黑框、无 UAC 弹窗。
- **触发器 2：用户登录时二次兜底 (`AtLogOn` + 5秒延迟)**
  - 针对 O+ Connect 等在用户登录桌面后重新激活转发的软件，在登录 5 秒后再次执行静默巡检并关闭转发，形成双保险闭环。
